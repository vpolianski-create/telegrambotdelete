# /verify — проверка «Умного Бусела»

Скилл построен по статье команды Claude Code
[«How the Claude Code team thinks about verification»](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/).
Главная мысль статьи: **запустить приложение и пройти по нему важнее тестов**. Сквозной сценарий трудно обмануть —
функция либо работает целиком, либо нет. Модульные тесты могут быть зелёными и при сломанной функции.

Цель — не «тесты зелёные», а уверенность, что приложение работает у Жени. Проект — `smart-busel/`
(команды — из `smart-busel/package.json`), правила проекта — `smart-busel/CLAUDE.md`, они действуют и здесь.

**Когда запускать:** перед каждым коммитом изменений в `smart-busel/`, перед «сливай» и по просьбе «проверь».
Это наш дымовой тест, поэтому он должен быть быстрым (~1 мин) и надёжным.

## Принципы

1. **Руки и глаза на настоящей программе.** Сценарии из `feature-map.md` идут в настоящем окне Electron: preload,
   `data.json`, IPC. Снимки экрана **смотреть** (Read) — у упавших шагов обязательно, у прошедших — выборочно.
2. **Сбой — словами.** Плохо: «Timeout 8000ms». Хорошо: «на действии „нажать «Дальше»“ экран урока не сменился за 8 с».
   К сбою прикладываются журнал действий (`trace` в `report.json`) и снимок экрана.
3. **Не больше 3 кругов исправлений.** Круг: найти причину → исправить → перезапустить `run.sh`.
   Следующий круг опирается на отчёт предыдущего (`<папка>/summary.txt`, `report.json`), а не начинает с нуля.
   После 3-го неудачного круга — остановиться и передать человеку **с причиной**.
4. **Исправлять причину, а не проверку.** Тест не подгонять и не удалять (CLAUDE.md). Если проверка устарела
   из-за решения родителя — менять её можно, но объяснить в отчёте.
5. **Нестабильность чинить, а не обходить.** Нельзя пропускать шаг, вставлять паузы или повторять «до зелёного»:
   сценарии ждут **признака** на экране (`waitFor`, `data-status`), а не времени. Если причину не найти —
   убрать сценарий, записать почему (в `feature-map.md` — «вручную: …») и поставить НУЖЕН ЧЕЛОВЕК.
6. **Изменение не правит свои проверки незаметно.** Если меняются `.claude/skills/verify/` или `smart-busel/tests/`,
   чек-лист (G1) это отмечает. `run.sh` прогоняет ещё и сценарии из `origin/main` (шаг 5b). Ослабление проверок —
   НУЖЕН ЧЕЛОВЕК.
7. **Проверка привязана к коммиту.** Отчёт называет коммит и незакоммиченные файлы. После новых правок прежний отчёт
   недействителен — перезапустить.
8. **Дешёвое — раньше дорогого.** Типы → контент → тесты → сборка → запуск → сценарии.
9. **Честный отчёт.** Что не проверено (нет устройства, нельзя здесь) — так и написать.

## Шаги

Всё автоматическое — один скрипт из корня репозитория:

```bash
bash .claude/skills/verify/run.sh /tmp/busel-verify      # папку отчёта можно не указывать
```

| № | Что | Команда (выполняет run.sh) | Пройдено, если |
|---|---|---|---|
| 0 | Окружение | `npm ci` (если нет node_modules), `node node_modules/electron/install.js` (если нет бинарника Electron) | без ошибок |
| 1a | «Линтер» интерфейса | `npx tsc --noEmit` | код 0. ESLint в проекте нет и **не ставить** без согласия родителя: строгий TypeScript — наш линтер |
| 1b | «Линтер» Electron | `npx tsc -p electron --noEmit` | код 0 |
| 1c | Учебный контент | `npm run validate-content` | код 0 |
| 2 | Тесты | `npm test` (vitest) | все прошли |
| 3 | Сборка | `npm run build` | код 0 |
| 4 | Запуск собранной версии | `xvfb-run -a node .claude/skills/verify/launch-check.cjs` | окно с `file://…/dist`, `window.busel` есть, ошибок страницы нет |
| 5 | Сценарии пользователя | dev-сервер `npx vite --port 5173` + `xvfb-run -a node .claude/skills/verify/scenarios.cjs <папка>` | все сценарии PASS (`scenarios/report.json`) |
| 5b | Сценарии из `origin/main` | то же, со `scenarios.cjs` из основной ветки — только если изменение правит саму проверку | все PASS |
| 6 | Чек-лист по изменениям | `node .claude/skills/verify/checklist.cjs` | нет «ОШИБКА»; каждое «ВНИМАНИЕ» и ручной пункт разобраны в отчёте |

Шаги 1–3 делает и сборка на GitHub (`.github/workflows/build-busel.yml`). Шаги 4–6 — то, чего GitHub не делает.

### Чек-лист по изменениям (`checklist.md`)

Пункты с признаком по путям изменённых файлов. Каждый пункт родился из реального промаха: например, V1 — выпуск
1.10.0 вышел без раздела в README родителя. `checklist.cjs` печатает только сработавшие пункты (обычно 2–5) и сам
проверяет автоматические. Ручные пункты агент проверяет по описанию и отмечает в отчёте. После каждого нового промаха —
отката, ошибки, найденной родителем, исправления после выпуска — добавить пункт. Устаревшие — убирать: проверки
«растут, только если им позволить».

### Круги исправлений (не больше 3)

Если `run.sh` вернул ошибку:

1. Открыть журнал упавшего шага (`<папка>/<шаг>.log`). Для шага 5 — строку FAIL (журнал действий и снимок) и сам
   снимок (Read).
2. Решить, чья это причина:
   - **дефект приложения** — исправить код. Для баллов, наград, ответов, сохранения, родительского режима и PIN —
     сначала тест (CLAUDE.md).
   - **дефект проверки** (сценарий устарел, неверный селектор, не закрыто окно) — исправить `scenarios.cjs` и объяснить
     в отчёте, почему это не прячет ошибку приложения.
   - **нельзя без человека** (учебный контент, внешний вид, новая библиотека, ключ, устройство) — сразу НУЖЕН ЧЕЛОВЕК.
3. Перезапустить `run.sh` целиком — это один круг. Сравнить с прошлым `summary.txt`: что ушло, что появилось.
4. После 3 кругов без полного успеха — НУЖЕН ЧЕЛОВЕК.

После правок в `scenarios.cjs` или в коде интерфейса прогнать `run.sh` ещё раз: два прогона подряд должны совпасть.

## Чего здесь проверить нельзя (в отчёте — «не проверено»)

- установщик Windows (`npm run dist`) и автообновление — только на Windows и GitHub Actions;
- APK на телефоне: поворот, вибрация, «Назад», вид на настоящем экране — сборка в GitHub Actions, телефон у родителя;
- печать на бумаге (проверяется лист грамоты и кнопка «Распечатать»);
- синхронизация с настоящим сервером Firebase (логика слияния покрыта тестами);
- на слух: озвучка мультуроков и ударения.

## Отчёт и вердикт

```
## /verify — <дата>; коммит <sha> (+N незакоммиченных файлов), ветка <имя>
| Шаг | Итог | Время | Доказательство |
|---|---|---|---|
| 1a TypeScript (интерфейс) | ✅ | 1 с | код 0 |
| …  | | | |
| 5 Сценарии | ✅ 11/11 | 40 с | scenarios/report.json, снимки |
| 6 Чек-лист | ✅ | 0 с | сработали U1, G1 — разобраны ниже |

Чек-лист: <по каждому сработавшему пункту — что проверено и как>.
Круги исправлений: N из 3 — что упало (словами), причина, что исправлено (файл:строка).
Нестабильные шаги: нет / какие и что сделано.
Не проверено: <из списка выше, если относится к изменению>.

**ИТОГ: ГОТОВО** — все шаги пройдены, повтор совпал, ручные пункты чек-листа закрыты.
или
**ИТОГ: НУЖЕН ЧЕЛОВЕК** — <что именно, почему, что посмотреть или решить родителю>.
```

**ГОТОВО** — только если:
- шаги 1–6 пройдены;
- каждое «ВНИМАНИЕ» чек-листа объяснено;
- в «не проверено» нет того, что напрямую затрагивает изменение. Например, правка Android-плагина без проверки на
  телефоне — это НУЖЕН ЧЕЛОВЕК.

Родителю итог пересказать простыми словами.

**Отметка в коммите.** В конце сообщения коммита ставится строка из вывода `run.sh`:
`Проверено: /verify — все шаги, сценарии 11/11 (на <sha> + правки)`. Если проверка не проводилась или не прошла —
`Проверено: нет — <причина>`. Так по истории видно, какие коммиты проверены.

## Как поддерживать

- Новый экран или важная функция — строка в `feature-map.md` (путь, селекторы, ожидаемый результат) и сценарий
  в `scenarios.cjs`: `step('Название', async () => { await act('что делаем', …); await see('что должны увидеть', …); return 'доказательство'; })`.
- Ожидания — только по признаку: `see`, `changed` (сменился экран), `data-status` задания. `waitForTimeout` и паузы
  не использовать.
- Сценарии запускают Electron с отдельной временной папкой `HOME` и начальными данными `SEED`: настоящие данные
  не трогаются.
- `data-answer` и `data-status` у задания есть только в dev-режиме Vite. Поэтому сценарии идут через dev-сервер,
  а собранная версия проверяется шагом 4.
- Всплывающие окна (награда «Ура!», новый уровень, слово Бусела «Хорошо») закрывает `dismiss()`: сначала окна
  `aria-modal`, потом баннеры, и каждый раз ждёт, пока окно исчезнет.
- Раз в несколько выпусков проверить сам скилл: ловит ли он прошлые промахи (например, V1 на копии с поднятой
  версией) и не стал ли медленнее.
