# /verify — проверка «Умного Бусела»

Цель — не «тесты зелёные», а **уверенность, что приложение работает у Жени**. Поэтому проверка идёт
от дешёвого к дорогому и заканчивается тем, что приложение запускается по-настоящему и по нему проходят,
как ребёнок и родитель. Каждый вывод подтверждается доказательством: вывод команды, файл данных, снимок экрана.

Проект — `smart-busel/` (команды — из `smart-busel/package.json`). Правила проекта — `smart-busel/CLAUDE.md`, их соблюдать и здесь.

## Принципы

1. **Проверяемые критерии.** Шаг считается пройденным только по объективному признаку (код выхода, PASS в отчёте,
   значение в `data.json`), а не «кажется, работает».
2. **Как пользователь.** Главное — сценарии из `feature-map.md` в настоящем окне Electron (preload, `data.json`, IPC),
   а не отдельные функции. Снимки экрана **смотреть** (Read), особенно у упавших шагов.
3. **Не больше 3 кругов исправлений.** Круг = найти причину → исправить код → перезапустить упавшее.
   После 3-го неудачного круга — остановиться и отдать человеку с описанием, а не «дожимать».
4. **Исправлять причину, а не тест.** Тест не подгонять и не удалять (CLAUDE.md). Если тест устарел из‑за
   **решения родителя**, менять его можно только с объяснением в отчёте.
5. **Нестабильность — тоже дефект.** Шаг, который то проходит, то нет, нельзя считать пройденным: найти причину
   (гонка, всплывающее окно, ожидание) и устранить; если не вышло — НУЖЕН ЧЕЛОВЕК.
6. **Честный отчёт.** Что не проверено (нет устройства, нельзя здесь) — так и написать.

## Шаги

Всё автоматическое делает один скрипт (из корня репозитория):

```bash
bash .claude/skills/verify/run.sh /tmp/busel-verify      # папку отчёта можно не указывать
```

| № | Что | Команда (выполняет run.sh) | Пройдено, если |
|---|---|---|---|
| 0 | Окружение | `npm ci` (если нет node_modules), `node node_modules/electron/install.js` (если нет бинарника) | без ошибок |
| 1a | «Линтер» интерфейса | `npx tsc --noEmit` | код 0. В проекте нет ESLint — **не ставить** без согласия родителя; строгий TypeScript — наш линтер |
| 1b | «Линтер» Electron | `npx tsc -p electron --noEmit` | код 0 |
| 1c | Учебный контент | `npm run validate-content` | код 0 |
| 2 | Тесты | `npm test` (vitest) | все прошли |
| 3 | Сборка | `npm run build` | код 0, есть `dist/` и `dist-electron/` |
| 4 | Запуск собранной версии | `xvfb-run -a node .claude/skills/verify/launch-check.cjs` | окно открылось с `file://…/dist`, `window.busel` есть, ошибок страницы нет |
| 5 | Сценарии пользователя | dev-сервер `npx vite --port 5173` + `xvfb-run -a node .claude/skills/verify/scenarios.cjs <папка>` | все сценарии PASS (`report.json`) |

Шаги 1–3 — то же, что делает сборка на GitHub (`.github/workflows/build-busel.yml`); шаги 4–5 — то, чего GitHub не делает.

### Круги исправлений (не больше 3)

Если `run.sh` вернул FAIL:

1. Открыть журнал упавшего шага (`<папка>/<шаг>.log`); для шага 5 — `scenarios/report.json` и снимок экрана упавшего сценария (Read).
2. Понять **причину** и решить, чья она:
   - **дефект приложения** → исправить код (для баллов, наград, ответов, сохранения, родительского режима, PIN — сначала тест, см. CLAUDE.md);
   - **дефект проверки** (сценарий устарел, неверный селектор, не закрыто всплывающее окно) → исправить `scenarios.cjs`, объяснить в отчёте, почему это не прячет ошибку приложения;
   - **нельзя без человека** (нужно менять учебный контент или внешний вид, ставить библиотеку, нужен ключ/устройство) → сразу НУЖЕН ЧЕЛОВЕК.
3. Перезапустить `run.sh` целиком (шаги зависят друг от друга). Это один круг.
4. После 3 кругов без полного успеха — остановиться: вердикт НУЖЕН ЧЕЛОВЕК.

### Проверка на стабильность

Перед тем как поставить ГОТОВО после правок в `scenarios.cjs` или в коде интерфейса — прогнать `run.sh` ещё раз:
результат двух прогонов подряд должен совпасть. Шаг, упавший хотя бы раз без изменения кода, — нестабильный (принцип 5).

## Чего здесь проверить нельзя (писать в отчёте как «не проверено»)

- установщик Windows (`npm run dist` — только на Windows/GitHub Actions) и автообновление;
- APK на телефоне (сборка — в GitHub Actions; телефон — у родителя), поворот экрана, вибрация, «Назад» Android;
- печать на бумаге (проверяется только наличие листа грамоты и кнопки «Распечатать»);
- синхронизация через Firebase с настоящим сервером (логика слияния покрыта тестами);
- на слух: озвучка мультуроков и ударения.

## Отчёт (формат)

```
## /verify — <дата>, коммит <short sha>, ветка <имя>
| Шаг | Итог | Время | Доказательство |
|---|---|---|---|
| 1a TypeScript (интерфейс) | ✅ | 6 с | код 0 |
| …  | | | |
| 5 Сценарии | ✅ 11/11 | 70 с | report.json, снимки: <папка>/scenarios |

Круги исправлений: N из 3 — что упало, причина, что исправлено (файл:строка).
Нестабильные шаги: нет / какие и что сделано.
Не проверено: (список из раздела выше, если относится к изменению).

**ИТОГ: ГОТОВО** — все шаги пройдены, повторный прогон совпал.
или
**ИТОГ: НУЖЕН ЧЕЛОВЕК** — <что именно и почему; что посмотреть/решить родителю>.
```

ГОТОВО ставится только если все шаги 1–5 пройдены, а в «не проверено» нет ничего, что затрагивает текущее изменение напрямую
(например, правка Android-плагина без проверки на телефоне — это НУЖЕН ЧЕЛОВЕК). Родителю пересказать итог простыми словами.

## Как поддерживать

- Новый экран или важная функция → строка в `feature-map.md` и сценарий в `scenarios.cjs` (по образцу: `step('Название', async () => { … return 'доказательство'; })`).
- Сценарии запускают Electron с отдельной временной папкой `HOME` и начальными данными `SEED` — настоящие данные не трогаются.
- `data-answer` у задания есть только в dev-режиме Vite — поэтому сценарии идут через dev-сервер, а собранная версия проверяется шагом 4.
- Всплывающие окна (награда «Ура!», новый уровень, слово Бусела «Хорошо») закрывает `dismiss()` — сначала окна `aria-modal`, потом баннеры.
